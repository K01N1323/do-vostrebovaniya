# Технический план игры «До востребования»

Дата: 15 октября 2026 года.

Основа: сюжетная библия v0.2 и подготовленная записка Корнишева Николая. Преподаватель разрешил использовать другую платформу вместо WebSim — это уточнение пользователя от 15 октября 2026 года учтено в выборе движка. Это проект архитектуры и задач разработки; программная реализация и проверка производительности ещё не выполнены. Вид от первого лица с фиксированным рабочим местом выбран здесь как рекомендуемый вариант из двух вариантов библии.

## Рекомендуемое решение

Сюжетная 3D-игра на Godot 4 с GDScript: игрок находится за столом бюро, переводит взгляд между окном выдачи, полками, столом и личным ящиком. Пакеты открываются, предметы приближаются и поворачиваются. Документы показываются крупными читаемыми панелями поверх сцены. Диалоги написаны заранее и выбираются по состоянию истории. Основная поставка — приложение для компьютера; сборку для браузера можно добавить после проверки основной версии.

Объём полной первой версии: одна комната, шесть NPC, восемь пакетов, два типа проверяемых бумаг, три финальных действия. Ориентир библии — 20–30 минут; фактическое время нужно измерить на прохождении. Нина появляется повторно, Вера и Леонид участвуют вместе, Серов остаётся доступен перед финалом.

Основная техническая задача — согласовать состояние вещей, знаний игрока, диалогов и финальных сцен. Сложность проекта определяется этим, а также удобством осмотра и качеством постановки.

Godot выбран потому, что комната, камера, свет, анимации, звук и интерфейс собираются в одном редакторе. Для нашего небольшого проекта это сокращает объём вспомогательного кода по сравнению с Three.js. Разрешение преподавателя снимает ограничение исходной лекции на WebSim. В будущей версии записки следует указать Godot; исходный документ в рамках этого анализа не изменяется.

Нужно установить официальный редактор Godot и шаблоны экспорта для выбранных платформ. Blender нужен для подготовки собственных моделей; серый прототип можно собрать средствами Godot. Конкретную стабильную версию движка фиксируем в README после пробного экспорта. Для первого варианта редактор Godot и Git покрывают основную разработку; дополнительные фреймворки не обязательны.

Отдельный сервер и база данных для этой версии не нужны. Поставка — локальная однопользовательская игра. Сохранение доступно на текущем устройстве; при ошибке записи игра продолжает работать в памяти и сообщает, что прогресс не сохранится. C++, C#, JavaScript и Python для основного кода не требуются. Python можно использовать позднее для вспомогательной обработки контента, если появится такая задача.

## Выбор движка

| Вариант | Оценка применительно к этой игре |
|---|---|
| Godot + GDScript | Основной выбор: визуальный редактор сцен, 3D, интерфейс, звук и экспорт приложения |
| Three.js + TypeScript | Альтернатива при приоритете браузера; больше собственных игровых и редакторских систем |
| Phaser | Разумный вариант при осознанном переходе к рисованному 2D-рабочему столу |
| Unity / Unreal | Для одной комнаты их дополнительные возможности не дают необходимой нам выгоды относительно объёма настройки и освоения |

GDScript выбран за простую интеграцию с Godot и достаточность для этой логики. Производительность будет в основном зависеть от графики и ресурсов, а не от языка обработки нескольких обращений. Для Godot 4 официальная документация на момент проверки указывает ограничение экспорта C#-проектов в Web; GDScript также оставляет возможность браузерной сборки.

## Слои приложения

```text
Мышь / клавиатура / кнопки интерфейса
                    ↓
Команда игрока → проверка допустимости → изменение GameState
                                            ↓
                         новая проекция сцены и интерфейса
                                            ↓
                      диалог / звук / сохранение / анимация

JSON-контент → проверка структуры и ссылок → игровые правила
```

GameState — единственное место хранения изменяемых игровых фактов. GameStore — единственный Autoload, который принимает команды, применяет правила и рассылает сигнал state_changed. Трёхмерные объекты и интерфейс отображают состояние, а не ведут собственные независимые копии истории. Например, исчезновение камеры со сцены следует из зарегистрированной выдачи, а не из прямого удаления объекта обработчиком кнопки.

Игровые правила реализованы обычными классами RefCounted и не зависят от конкретного дерева 3D-сцены. Тест может провести смену и проверить финал в headless Godot без загрузки комнаты. Рисование, звук, сохранение и анимации подключены как внешние исполнители. Между узлами используются явные сигналы, без десятков глобальных менеджеров.

### Три разных вида информации

1. Неизменные авторские факты: настоящий владелец, содержимое, прошлое Павла, причины появления находок. Они находятся в контенте и не меняются от решений игрока.
2. Наблюдения игрока: какие признаки он осмотрел, какие бумаги прочитал и какие реплики услышал. Они открывают новые темы разговора, но не создают новые факты прошлого.
3. Текущие последствия: кому выдан пакет, где карточка, кто ждёт у окна и завершена ли сцена.

В авторских данных можно хранить имя настоящего владельца для проверки контента. Интерфейс не должен автоматически показывать его, определять вора или выводить нравственную оценку. При доступе к файлам проекта скрытый контент можно прочесть; защита от такого чтения для учебной версии не требуется.

## Что конкретно реализовать

### 1. Рабочее место и управление

Создать стол, окно выдачи, полки, архивную папку, место для временного осмотра и личное место под столом. Предусмотреть четыре положения камеры: окно, полки, стол и личное место. Переходы плавные, без обязательного свободного перемещения. Содержимое должно читаться и на обычном экране ноутбука.

InteractionController определяет объект под указателем лучом от Camera3D через PhysicsDirectSpaceState3D, подсвечивает разрешённое действие и отправляет команду ядру. Нажатие на бумагу открывает DocumentPanel, на пакет — действие с пакетом. Когда открыта модальная панель, сцена не принимает нажатия сквозь неё: Control поглощает событие, обработка 3D-ввода проверяет режим UI. Повторное нажатие во время операции не должно выдавать пакет повторно.

Первый вариант перемещения — нажать на пакет, затем выбрать доступное место. Перетаскивание можно добавить после проверки удобства: свободная физика для этого не нужна. По Escape закрывается текущий осмотр или открывается пауза.

### 2. Реестр вещей

Зарегистрировать P01–P08 со стабильными ID. Состояние P08 в начале — «ещё не поступил». Его нельзя выбрать, увидеть на полке или открыть до соответствующей сцены.

| Пакет | Реализуемое содержимое и важные признаки |
|---|---|
| P01 | Переноска, три бутерброда, блюдце с надломленным краем, салфетка с голубой заплатой |
| P02 | Кирпич со скошенным углом, белой штукатуркой и синей краской; рабочая рубашка с тёмной заплаткой на воротнике |
| P03 | Почти пустой общий чемодан, зелёное пятно, отломанный язычок под подкладкой; код замка знает Леонид |
| P04 | Серебристая камера, штопаный тканевый ремешок, три луковицы; Глеб заявляет чёрную камеру и два рулона плёнки |
| P05 | Личное пальто под ошибочной пометкой «служебное»; 13 пустых карманов, белая двойная штопка справа, неверно пришитый узкий карман |
| P06 | Чёрный чехол без камеры, резиновая крышка; похожая находка для поиска |
| P07 | Пять разных телевизионных пультов без батареек, стянутых резинкой |
| P08 | Синяя сумка Павла, белая рубашка, старый неиспользованный билет, пропуск стажёра и карточка №314 |

Для пальто можно использовать общий вид подкладки с кликабельными карманами; моделировать тринадцать физических тканевых полостей не требуется. Важные признаки доступны до решения. Их осмотр открывает вопросы в диалоге, но не показывает метку «вор» или «честный».

У пакета всегда одно местонахождение. Выданный пакет недоступен для повторной выдачи. Возврат на хранение перемещает его со стола на полку. Присвоение переносит его в личное место, где он остаётся виден в конце.

### 3. Обращения и документы

Обращение хранит список претендентов, предъявленные документы, выбранный пакет и результат. Для Мельниковых у одного обращения два претендента и два заявления. Выдать P03 можно Вере, Леониду либо оставить на хранении. У этого случая нет скрытой единственно правильной стороны.

DocumentSystem отдельно хранит поля удостоверения и заявления. Игрок может открыть их рядом и вручную сравнить имя и описание. Система может запоминать отмеченные им несоответствия, но не обязана автоматически решать обращение. У Глеба настоящие документы и совпадающее имя; расхождение находится в описании содержимого.

Старый акт, пропуск Павла, билет и карточка №314 — читаемые сюжетные предметы. Они не добавляют ещё четыре типа процедурных проверок. Русский текст документов показывается через Control и RichTextLabel с шрифтом с кириллицей; мелкая надпись на 3D-текстуре не должна быть единственным способом чтения.

### 4. Диалоги

Узел содержит говорящего, текст, доступные вопросы, условие показа, переход и разрешённые эффекты. Условия выражаются ограниченными структурированными данными: «прочитан документ», «осмотрен признак», «пакет выдан этому человеку». Произвольный код из JSON не исполняется.

Нужно поддержать две функции: перейти к следующей реплике и выбрать вопрос. Вопрос может появиться после осмотра предмета. Реплика не должна внезапно сообщать знание, которого у героя нет по канону. Однажды выполненный сюжетный эффект не повторяется при повторном открытии реплики или загрузке.

Обязательные разговоры: обучение с Ниной, кирпич Фёдора, совместная сцена Веры и Леонида, противоречие Глеба, пальто и прошлое Серова, поступление сумки Павла, три финальных маршрута. Семь грехов остаются в авторских заметках; их названия не появляются в игровом интерфейсе.

### 5. Режиссёр смены

StoryDirector запускает следующую сцену после завершения обращения и необходимых реплик. Возврат вещи на хранение и присвоение тоже позволяют завершить обращение. «Вернуть на полку, пока думаю» и «завершить обращение без выдачи» — разные команды, иначе простая перестановка пакета будет случайно выгонять посетителя.

Порядок: начало → Нина → Фёдор → Мельниковы → Глеб → Серов → Нина с P08 → финальное действие. В начале Нина упоминает разбор старой комнаты. После обращения Серов переходит в состояние ожидания рейса и остаётся доступен независимо от того, выдали ли ему пальто.

Автобус в первой версии является сценарием и звуковой постановкой. Реальный таймер не должен незаметно лишать игрока финальной передачи, пока тот читает бумаги.

### 6. Концовки и последствия

EndingSystem получает явное решение о карточке и читает текущие положения вещей. Нужно реализовать три маршрута:

1. Карточка передана Серову. При этом пальто появляется у него только если P05 действительно был выдан ему.
2. Карточка помещена в архив с подписанным дополнением. Старый ложный акт остаётся рядом, а не заменяется новым.
3. Павел забирает свою сумку вместе с карточкой. Если карточка была вынута для чтения, система возвращает её в сумку при завершении этого действия.

Все три действия становятся доступны после сюжетного раскрытия P08 и чтения карточки. При передаче Серову или в архив карточка покидает сумку; копия ради финального кадра не создаётся. Не нужно назначать концовку по числу «хороших» выдач.

В финале остаются локальные последствия: камера могла уйти с Глебом, чемодан — одному из Мельниковых, пальто — остаться на полке, присвоенные вещи — лежать под столом. Передача карточки не отменяет этих фактов, прошлое осуждение и семейные обстоятельства Серова.

### 7. Сохранение и восстановление

SaveRepository через FileAccess записывает в user://save.json версию формата, ID сцены, прогресс диалога, положения предметов, обнаруженные признаки и результат решений. Сначала записывается временный файл, проверяется результат записи, затем заменяется основное сохранение с обработкой ошибки. В сохранение не попадают Node, Mesh, текстуры, таймеры анимации и другие объекты движка. После загрузки комната строится по состоянию.

Сохранять после законченной команды и стабильных переходов сцен. Загрузка не должна заново исполнять эффекты уже завершённых узлов. Для маленькой игры достаточно снимка состояния; полную систему восстановления из журнала событий строить не требуется.

Проверить JSON, версию и согласованность сохранения. При повреждении показать выбор новой игры, не завершать приложение аварийно. При недоступном файле продолжать с текущим прогрессом в памяти.

### 8. Графика и звук

Начать с примитивов и подписей; затем заменить ключевые предметы на простые GLB-модели. Поворот предмета, открытие крышки, движение в зону выдачи и реакция NPC создаются заранее заданными анимациями. Полная физика, ткань, захват предметов руками и сложная лицевая анимация в первый объём не входят.

Шесть NPC должны различаться силуэтом, одеждой, позой и манерой реплик. Для первого рабочего прохождения достаточно бюстов или статичных фигур с несколькими позами. Полная озвучка не нужна; субтитры остаются основным носителем разговора.

Звуки: помещение, лампа, шаги, бумага, упаковка, ящик, вокзальное объявление. AudioStreamPlayer воспроизводит фон и интерфейсные звуки, AudioStreamPlayer3D — источники в комнате. Звук активируется после нажатия «Начать». Важные сведения продублированы текстом. Предусмотреть громкость, отключение звука и уменьшение движения камеры.

Целевой технический ориентир: стабильные 30 кадров/с и читаемый интерфейс на выбранном для защиты ноутбуке. Это цель приёмки, а не измеренный результат; перед полировкой нужно замерить загрузку и частоту кадров. Основная проверка — экспортированное приложение, а не только запуск из редактора. Браузерные проверки добавляются, если будет нужна Web-сборка.

## Пример контракта ядра

Ниже схема типов, а не готовая реализация:

```gdscript
# game_command.gd
class_name GameCommand
extends RefCounted

enum Kind {
    MOVE_PACKAGE, OPEN_PACKAGE, INSPECT_DETAIL, READ_DOCUMENT,
    CHOOSE_REPLY, ISSUE_PACKAGE, RETAIN_PACKAGE,
    APPROPRIATE_PACKAGE, CHOOSE_ENDING
}

var kind: Kind
var payload: Dictionary

# Пример данных команды ISSUE_PACKAGE:
# {"case_id": "gleb_case", "package_id": "P04", "recipient": "gleb"}

# game_store.gd — отдельный файл, схема публичного интерфейса
# extends Node
# signal state_changed
# signal command_rejected(reason: String)
# func dispatch(command: GameCommand) -> void
# func get_snapshot() -> Dictionary

# state_reducer.gd — отдельный файл, без зависимости от 3D-узлов
# class_name StateReducer
# extends RefCounted
# func apply_command(state: Dictionary, command: GameCommand) -> Dictionary
# Результат: {"ok": bool, "state": Dictionary, "effects": Array,
#             "error": String}
```

Перед обновлением проверить существование ID, активное обращение, присутствие пакета, разрешённость команды в текущем режиме и отсутствие уже принятого решения. Для выдачи нужно выбрать явного получателя. Отказ по техническому состоянию возвращает объяснение, состояние не изменяется.

Не следует запрещать выдачу Глебу на основании авторского знания о настоящем владельце: игрок вправе совершить эту ошибку. Техническая допустимость и правота решения — разные проверки.

Результат содержит новое состояние и эффекты для представления: звук, анимацию, сохранение. GameStore публикует снимок; представление не получает ссылку, через которую может незаметно изменить исходное состояние. Вечное хранение двух независимых значений вроде `camera_given_to_gleb` и положения P04 не требуется: такое условие вычисляется из положения пакета. Стартовый вариант хранения состояния — вложенные Dictionary с явной валидацией полей и глубоким копированием на границах; при росте проекта их можно заменить типизированными классами.

Карточка является отдельной сущностью внутри P08. Пока она в сумке, её положение следует за положением сумки. После изъятия её положение учитывается отдельно. Это предотвращает появление документа одновременно у Серова и в личной сумке.

### Публичные операции модулей

| Файл | Что написать |
|---|---|
| game_store.gd | dispatch(command), get_snapshot(), сигналы state_changed и command_rejected; единственный вход для игровых изменений |
| state_reducer.gd | apply_command(state, command): проверить команду, создать новое состояние, вернуть результат и эффекты |
| package_system.gd | can_move(state, package_id, target), can_issue(state, case_id, package_id, recipient); правила местонахождений и получателей |
| inspection_system.gd | get_available_details(state, package_id), can_inspect(state, package_id, detail_id); доступность открытия и признаков |
| document_system.gd | get_document_view(state, document_id), get_presented_documents(state, case_id); содержание панелей без автоматического вердикта |
| dialogue_system.gd | get_current_node(state), get_available_choices(state), validate_choice(state, node_id, choice_id) |
| story_director.gd | get_next_scene(state), can_finish_case(state), get_scene_entry_effects(scene_id); переходы только после выполнения условий |
| ending_system.gd | get_available_endings(state), build_ending_view(state); финальная постановка из фактического состояния |
| save_repository.gd | save_snapshot(snapshot), load_snapshot(); результат с признаком успеха и причиной ошибки |
| content_validator.gd | validate_content(data); уникальность ID, обязательные поля, существование ссылок и достижимость обязательных узлов |
| interaction_controller.gd | pick_target(screen_position), request_interaction(target); выбор узла и отправка команды без самостоятельной выдачи вещи |

Все функции правил читают переданное состояние; изменения выполняет reducer через GameStore. Контракты уточняются до параллельной разработки. Тестовый runner должен собирать список ошибок и завершаться ненулевым кодом при провале, чтобы проверки работали и без редактора.

## Архитектура агентов разработки

Под агентами здесь понимаются исполнители разработки. Для персонажей игры используются сценарные состояния «пришёл», «разговаривает», «ждёт», «ушёл» и условия диалогов. Вызовы языковой модели во время прохождения для этой версии не нужны: они добавили бы изменчивость фактов, задержки и зависимость от сервиса. ГенИИ участвует в подготовке и проверке контента и кода.

| Агент | Ответственность | Область изменений | Результат приёмки |
|---|---|---|---|
| Архитектор и интегратор | Контракты, сборка, границы модулей, интеграция | project.godot, main.tscn, game_command.gd, docs/contracts.md | Модули подключаются через согласованные интерфейсы |
| Разработчик игровой логики | Состояние, перемещения, обращения, финалы, сохранения | core за исключением общих контрактов, case_system.gd, package_system.gd, ending_system.gd, persistence | Смена и три финала проходятся в headless-тестах |
| Разработчик 3D и взаимодействий | Комната, камера, осмотр, ресурсы, звук | scenes/room, scenes/objects, scenes/characters, presentation, inspection_system.gd, assets | Каждая важная деталь доступна; сцена следует GameState |
| Сценарист и разработчик диалогов | Канон, содержание пакетов, тексты, условия сцен | data, scripts/content, dialogue_system.gd, story_director.gd, docs/canon.md | Все сюжетные переходы и знания героев согласованы |
| Разработчик интерфейса | Документы, диалоги, журнал, решения, пауза | scenes/ui, scripts/ui, document_system.gd | Можно прочесть бумаги и закончить обращение без действий сквозь панели |
| Тестировщик и рецензент | Проверка веток, сохранений, доступности улик и сборки | tests, список дефектов, docs/acceptance.md | Найдены и воспроизводимо проверены противоречия состояния |

Авторство разных систем не означает право менять общие типы по своему усмотрению. Изменение публичного контракта сначала согласовывает интегратор. Тестировщик направляет дефекты владельцу модуля; правки в чужих областях отдельно координируются.

### Порядок совместной работы

1. Сначала архитектор фиксирует ID, команды, структуру контента и критерии приёмки. Сценарист проверяет их по канону.
2. Разработчик логики делает P01 и полный цикл обращения на заглушках. Это первая точка интеграции. Каждый агент меняет собственные подсцены; главную main.tscn собирает только интегратор, чтобы избежать конфликтов текстового формата сцен.
3. После фиксации контракта параллельно развиваются логика, представление и контент с интерфейсом. Количество одновременно работающих исполнителей можно ограничить тремя; шесть ролей не требуют шести одновременных запусков.
4. Интегратор соединяет завершённые изменения небольшими порциями. Файлы конфигурации и общие типы принадлежат одному владельцу.
5. Тестировщик проходит ветви и возвращает конкретный сценарий ошибки. Исправления принимает владелец системы, затем повторяется связанная проверка.
6. После каждой итерации сохраняются рабочая версия, краткий результат и использованные запросы к ГенИИ.

### Что получает каждый агент

Общий пакет: утверждённый канон, контракты команд, список принадлежащих ему файлов, входные зависимости, задача текущей итерации и проверяемый результат. В отчёте агента нужны изменённые файлы, выполненные проверки и нерешённые вопросы. Постоянный свободный обмен всех агентов между собой не требуется: решения о составе системы собирает интегратор.

Пример задания разработчику логики: «Реализовать выдачу, хранение и присвоение пакета в активном обращении. Сохранить единственное местонахождение предмета. Не ограничивать выдачу истинным владельцем. Проверить повторное нажатие и уже выданный пакет. Работать на GDScript с классами правил без привязки к 3D-дереву. Не изменять UI, сцены комнаты и публичные контракты без согласования».

Пример задания сценарному агенту: «Подготовить обращение Глеба по v0.2. Настоящее имя совпадает в бумагах, описание расходится с серебристой камерой и луком. Ремонт лампы был настоящим добрым поступком. После осмотра открыть вопрос о содержимом. Не связывать Глеба с преступлением 2014 года».

Пример задания агенту представления: «Показать P05 по состоянию пакета. Дать осмотреть тринадцать карманов и штопку. Все решения отправлять как команды. В финальном кадре не создавать пальто у Серова, если оно осталось в бюро».

|---|---|---|
| 0 | Создать Godot-проект, выбрать рендерер, загрузить пробный GLB, показать UI с кириллицей, экспортировать приложение | Подтверждён запуск игры на компьютере для защиты |
| 1 | Серое рабочее место, Нина, P01, удостоверение, заявление, осмотр и три решения | Новую игру можно начать и завершить первое обращение |
| 2 | P02–P07, остальные обращения, общий чемодан, ветки Глеба и Серова | Основной цикл выдерживает разные решения; Серов ждёт рейс |
| 3 | P08, акт и карточка, три финала, сохранение и загрузка | Доступны все три действия; последствия выдач не теряются |
| 4 | Финальные модели, свет, звук, реакции NPC, настройка читаемости | Полное прохождение понятно и атмосферно; измерены загрузка и частота кадров |
| 5 | Проверка маршрутов, экспорт приложения, инструкция, история ГенИИ-итераций, материалы к защите | Рабочая версия соответствует согласованным требованиям БДЗ |

Первая итерация проверяет удовольствие от осмотра, чтения и выдачи. Она ещё не представляет весь сюжет. Если работа со столом неудобна, сначала исправляется она; красивые ресурсы добавляются после этого.

## Обязательные проверки

- Нельзя открыть P08 до его поступления или выдать пакет дважды.
- Возврат со стола на полку не завершает обращение без явного решения.
- Выдача P04 Глебу допустима как выбор игрока и действительно убирает камеру из бюро.
- У P03 доступны оба претендента; выбранный получатель сохраняется после загрузки.
- Доступ к Серову в финале сохраняется после отказа в P05 и после его присвоения.
- Варианты с выданным, оставленным и присвоенным P05 корректно отображаются во всех трёх финалах.
- Карточка существует в одном экземпляре; после передачи её нет внутри P08.
- Архивный маршрут сохраняет старый акт и добавляет отдельное подписанное дополнение.
- Сохранение после решений и во время чтения восстанавливает те же сведения без повторной выдачи или повторного поступления P08.
- Несуществующие ссылки диалогов, недостижимые обязательные сцены и неправильные ID пакетов обнаруживаются проверкой контента.
- Игра завершается при использовании «оставить на хранении» во всех обычных обращениях; отказ не создаёт тупик.
- Текст документов читаем при изменении размера окна; панели не пропускают нажатия в сцену.
- Без звука остаются доступны все важные сведения; отклонённое воспроизведение звука не останавливает игру.

Автоматически проверить сочетания трёх финалов с тремя исходами P05. Отдельно проверить выдачу P04, три исхода общего чемодана и сохранение после каждого значимого перехода. Все комбинации декоративных анимаций перебирать не нужно.

## Стартовое задание для первой итерации

Создай первый играбельный прототип русскоязычной игры «До востребования» на стабильной версии Godot 4 с GDScript и рендерером Compatibility. Используй отдельные сцены комнаты, камеры, пакета, осмотра и UI. Игрок работает за столом бюро находок старого автовокзала. Камера переводится между окном выдачи, полкой, столом и личным местом под столом через Tween. Интерфейс с кириллицей реализуй на Control в CanvasLayer.

Реализуй только первое обращение Нины. На полке стоит P01: кошачья переноска, внутри три бутерброда на блюдце с надломленным краем и салфетка с голубой заплатой. Никакого кота внутри нет. У Нины есть удостоверение и заявление с совпадающим именем. Позволь прочесть обе бумаги, переместить переноску на стол, открыть и осмотреть содержимое, затем выдать Нине, завершить обращение с оставлением на хранении или присвоить переноску. Простое возвращение на полку во время осмотра не должно завершать обращение.

Состояние игры храни отдельно от 3D-объектов в GameStore. Любое решение обновляет его через команду; сцена и интерфейс обновляются по сигналу state_changed. Правила оформи классами RefCounted. У пакета одно местонахождение, повторная выдача невозможна. Техническая проверка разрешённости команды не оценивает нравственность решения. Документы показывай крупным текстом поверх сцены. На время открытого документа блокируй нажатия по предметам за ним.

Используй простую геометрию и несколько коротких бытовых реплик. Нина заранее упоминает разбор старой комнаты. После решения покажи её реакцию и завершение первого обращения. Все надписи на русском. Предусмотри управление мышью, Escape для выхода из осмотра, начало звука только после нажатия «Начать» и возможность играть без звука. На этом этапе не добавляй остальных посетителей и финальное раскрытие.
